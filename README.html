Bakery Order Tracker

A local app that helps a home baker turn Instagram DMs into a workable order plan without exceeding oven time or missing notice requirements.

Return to the bakery app

Start the app

  1. Open Terminal in this folder.
  2. Run python3 app.py (on Windows, run python app.py).
  3. Open http://127.0.0.1:8000 in a browser.

Stop the app by returning to Terminal and pressing Ctrl+C.

No installation is needed. The app uses only Python’s standard library and runs entirely on this computer.

What the app does

  • Imports the 13 starting orders from existing_orders.csv.
  • Fetches messages from the seven Instagram HTML files without creating duplicates.
  • Shows daily oven use, order revenue, and helper capacity.
  • Checks each new order, change, or cancellation against the two-day notice rule.
  • Checks whether a new or changed order fits the day’s available oven time.
  • Lets the baker accept or reject requests one at a time, or process one message day in sequence.
  • Lets the baker book a helper for $100, adding four hours to a pickup day.
  • Tracks accepted, rejected, changed, cancelled, and picked-up orders.

How to use it

  1. Start on Dashboard to see capacity by pickup day.
  2. Set the Working date in the top right. It controls the day processed by “Accept compatible requests” and the notice date for helper bookings.
  3. Open DM inbox and choose Fetch new DMs. Repeating this is safe: an existing message is not duplicated.
  4. A green “Ready to take” label means the request obeys both rules. A red label explains the conflict.
  5. Accept or reject requests one at a time, or choose Accept compatible requests · next day. That action processes the selected message day in order, rejects rule conflicts, and moves the working date forward.
  6. If a day needs more capacity, book a helper from that day’s card and review the recommendations again.
  7. Open Orders to review the order book and mark completed orders Picked up.

Plan used before building

  1. Purpose: track pending orders, available capacity, valid changes and cancellations, revenue, and helper costs.
  2. Front end: put daily capacity first; put the facts beside each accept/reject action; keep one button per action.
  3. Database: store each fact once in linked orders, requests, and helpers tables. Calculate daily totals instead of duplicating them.
  4. Back end: implement notice, capacity, helper, decision, cancellation, and pickup transitions as small functions.
  5. Testing: use a copied database; verify import counts, calculations, state transitions, API responses, and browser layout.

Implementation details

app.py contains the three labelled parts: front-end HTML/CSS/JavaScript, back-end rule and action functions, and database/external-data functions. It creates bakery.db the first time it runs. Later runs reuse the same database, so decisions are preserved. Safe schema migrations add new fields without replacing existing data.

The browser uses these JSON routes: GET /api/state, POST /api/fetch, POST /api/request/decision, POST /api/accept-day, POST /api/helper, and POST /api/order/picked-up. There is no AI inside the app and no external network request.

Test plan

  • Database/external data: confirm 13 starting orders and 25 unique Instagram messages; repeat fetch and confirm zero duplicates.
  • Rules: check one valid request and one request with only one day’s notice; verify oven capacity with and without a helper.
  • Transitions: accept, reject, accept a whole message day, cancel, change, and mark picked up.
  • Queries: verify Friday hours remaining, weekly revenue, active order count, and helper cost from stored records.
  • Front end: check every view and button in a desktop browser, then inspect the narrow responsive layout.
  • Safety: run all mutation tests on a copy of bakery.db, never the real database.

Data and safety

All information stays in bakery.db in this folder. For testing, use a copy of that file. To start over manually, stop the server, make a backup, then remove bakery.db; the next start will import the original CSV and Instagram files again.

Project goal and constraints

The goal is to help a non-technical home baker track orders received by Instagram DM, understand which requests can be accepted, and plan each pickup day. The solution is intentionally one Python file, one SQLite database, and a plain browser interface. It uses no Node.js, packages, cloud services, or AI decisions.
